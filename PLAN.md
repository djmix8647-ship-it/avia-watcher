# PLAN: avia-watcher — Telegram-алерты на аномально дешёвые авиабилеты

## Goal

24/7 Python-демон: опрашивает Travelpayouts (Aviasales) API по заданным маршрутам,
хранит историю цен в SQLite, и при обнаружении цены существенно ниже скользящей
медианы — шлёт алерт в Telegram с ценой, датами, маршрутом и ссылкой на билет.
Один процесс, `requests` + `sqlite3` (stdlib) only, без фреймворков.

## Observable acceptance criteria

1. `python test_watcher.py` завершается без ошибок (assert-based self-check),
   включая детерминированный тест `check_route` на замоканном HTTP-ответе
   (без реальной сети) — проверяет весь путь fetch → record → anomaly → alert
   → dedup.
2. Запуск `python watcher.py` с валидными токенами в `.env`:
   - непрерывно опрашивает все маршруты из `config.py` с интервалом
     `POLL_INTERVAL_SECONDS`/`EFFECTIVE_INTERVAL` и не завершается при разовой
     сетевой/API ошибке, HTTP 429 или зависшем соединении — каждый HTTP-запрос
     (и к Travelpayouts, и к Telegram) имеет конечный `timeout`
     (`REQUEST_TIMEOUT_SECONDS`, по умолчанию 10с); таймаут ловится той же
     веткой `requests.RequestException`, что и обычные сетевые ошибки;
   - каждое **успешно полученное** наблюдение пишется в `prices.db`
     (переживает перезапуск процесса) — независимо от того, сработал ли по
     нему алерт, провалилась ли попытка отправки в Telegram, или аномалии не
     было вовсе; единственный случай, когда наблюдение не пишется — сам
     `fetch_cheapest` не вернул данных (сеть/429/пустой ответ/нераспознанная
     схема);
   - при цене ниже `ANOMALY_THRESHOLD * median(history)` (и только когда
     история этой точной конфигурации маршрута накопила `MIN_HISTORY_SAMPLES`
     наблюдений, и только для записей с `actual != false`) отправляет
     сообщение в Telegram с ценой, датами, маршрутом и ссылкой на билет —
     и не повторяет алерт для уже подтверждённо отправленной (`status='sent'`)
     комбинации цена+даты+маршрут в рамках обычной работы и после падения
     процесса с последующим перезапуском. Единственное принятое и явно
     задокументированное исключение — редкий дубль, если процесс аварийно
     упал **строго между** подтверждённой доставкой в Telegram и локальным
     `UPDATE ... SET status='sent'` (окно в доли секунды); это компромисс в
     пользу того, чтобы обычный сбой сети к Telegram не терял алерт навсегда
     (см. «Дедупликация и порядок доставки»).
3. Детерминированная проверка аномалии — юнит-тест с замоканным ответом API
   (не полагается на живой рынок билетов, см. verification).
   Отдельно, вручную, на реальных токенах: наблюдательная проверка, что при
   искусственно ослабленном пороге процесс присылает сообщение в Telegram
   в течение нескольких циклов (не гарантируется ровно один цикл — зависит
   от кэша API).
4. Смена маршрута/порога — правка `config.py`, без изменения кода `watcher.py`.
5. `.env` не закоммичен (есть `.gitignore`), токены только через переменные
   окружения / `.env`.

## Approach

### Источник данных (пересмотрено после ревью, round 1)

Первая версия плана отклонила `aviasales/v3/prices_for_dates` как
несуществующий на основании чтения зеркала документации на GitHub
(`github.com/travelpayouts/slate`) — тот репозиторий эндпоинт не описывает.
Ревьюер (Codex) указал, что эндпоинт реально существует и рекомендован
официально. Проверено эмпирически прямым запросом к живому API без токена:

```
GET /aviasales/v3/prices_for_dates?origin=MOW&destination=LED&token=invalid → HTTP 401 Unauthorized
GET /v2/prices/latest?origin=MOW&destination=LED&token=invalid             → HTTP 401 Unauthorized (для сравнения, заведомо реальный)
GET /aviasales/v3/totally_made_up_endpoint_xyz?token=invalid               → HTTP 404 Not Found (для сравнения, заведомо фейковый)
```

401 (а не 404) подтверждает, что путь существует и требует лишь валидный
токен — берём этот эндпоинт как основной источник данных.

**`GET https://api.travelpayouts.com/aviasales/v3/prices_for_dates`**
— самые дешёвые билеты, найденные пользователями Aviasales за последние
48 часов, по конкретным датам (не только по месяцу целиком, в отличие от
`/v2/prices/latest`).

Параметры запроса (подтверждено независимо в двух источниках: пример из
поисковой выдачи с полным списком параметров и реализация в открытом Python-
wrapper `richarah/aviasales-python`, файл `api.py`, функция `prices_for_dates`):
`origin`, `destination`, `departure_at` (`YYYY-MM` или `YYYY-MM-DD`),
`return_at` (опционально, для one-way не передаётся), `one_way` (`true`/`false`),
`direct` (`true`/`false`), `sorting` (`price`/`route`), `unique`, `limit`,
`page`, `currency` (по аналогии со всеми остальными эндпоинтами семейства —
единственный параметр, для которого не нашлось прямого примера с этим именно
эндпоинтом; см. риски ниже), `token`.

Поле точной схемы ответа (в частности, имя поля со ссылкой на билет) не
удалось подтвердить документацией — Help Center (`support.travelpayouts.com`)
был недоступен из этой сессии (DNS-ошибка при попытке), а открытые обёртки
не парсят ответ детально. Реализация делает разумное предположение на основе
паттерна, общего для всего семейства v1/v2 API (`price`/`value`,
`departure_at`, `return_at`, `origin`, `destination`, `actual`) плюс поле
`link` (относительный путь, требующий склейки с `https://www.aviasales.com`)
— и **защищается фолбэком, с громким (не тихим) сигналом об этом
(устраняет REV-016)**: `fetch_cheapest` различает два разных «пусто»:
(a) API вернул `data: []` — обычная ситуация (для этих дат правда нет
предложений), тихий `log.info`, `check_route` просто ничего не пишет в этот
цикл; (b) API вернул непустой `data`, но ни в одном элементе не нашлось
распознаваемого поля цены (`price`/`value`) — это отличается от «нет
данных» тем, что схема ответа не совпала с ожидаемой, и демон в таком
состоянии может работать сколь угодно долго, не находя вообще ничего, даже
с правильными токенами. Такой случай логируется **отдельной строкой на
уровне ERROR** (не `info`, не «затерялось» в обычном потоке), один раз на
маршрут за цикл, с перечислением реальных ключей первого элемента ответа —
чтобы это было невозможно не заметить в логах systemd/journalctl, но
процесс всё равно не падает (24/7-требование сильнее). `fetch_cheapest`
возвращает `None` в обоих случаях (a) и (b), различается только уровень и
текст лога. Если есть цена, но нет `link`, используется резервная ссылка на
страницу поиска маршрута
(`search.aviasales.ru/?marker=&origin_iata=&destination_iata=&locale=ru`,
задокументирована в `_additional.md` репозитория travelpayouts/slate, поле
`choose_dates_url`). Первый реальный запуск с настоящим токеном (см.
verification, шаг 1) **обязателен** до продакшен-использования именно для
того, чтобы отличить (a) от (b) на реальном ответе и при необходимости
поправить имена полей — это явно вынесено в README как первый шаг после
установки, и README прямо указывает: если в логе появилась ERROR-строка о
нераспознанной схеме — это сигнал остановиться и поправить код, а не
работающий в фоне демон, который просто "молчит".

### Устойчивость и корректность (пункты ревью round 1 + round 2)

- **Идентичность маршрута** (`route_id`) включает `origin`, `destination`,
  `departure_at`, `return_at`, `one_way`, `currency` — разные валюты/типы
  поездки для одного и того же города не смешивают историю цен и медиану.

- **Порядок решения в `check_route` (устраняет REV-011 и REV-020, явная
  семантика)**: разбит на «основной путь» (шаги 1–5, только когда API
  ответил) и «доставка отложенных алертов» (шаг 6), которая **не вложена**
  внутрь основного пути и выполняется, даже если шаг 1 не дал данных —
  именно это было упущено в предыдущей редакции (REV-020: `flush` был
  описан как безусловный, но при этом жил внутри ветки "если `entry` не
  `None`", то есть фактически пропускался при сбое API/429, ровно тогда,
  когда Telegram мог уже восстановиться, а отправленный ранее pending-алерт
  так и не долетал).
  1. `entry = fetch_cheapest(route)` — может быть `None`
     (сеть/таймаут/429/пусто/нераспознанная схема).
  2. **Только если `entry is not None`**: `history = get_recent_prices(conn,
     rid, HISTORY_WINDOW)` — последние `HISTORY_WINDOW` уже сохранённых
     ранее наблюдений (`actual IS NULL OR actual = 1`); текущий `entry` в
     эту выборку не входит.
  3. Если `entry.get("actual") is False` → анализ аномалии пропускается
     (шаг 4), но запись всё равно попадёт в БД на шаге 5.
  4. Если `entry` актуален и `len(history) >= MIN_HISTORY_SAMPLES`:
     `anomaly, baseline = is_anomaly(entry_price, history, ANOMALY_THRESHOLD)`;
     при `anomaly=True` — `claim_alert(conn, rid, route, entry)`: считает
     `purchase_url, is_itinerary_specific = build_purchase_link(route,
     entry)` **прямо сейчас, пока есть исходный `entry` с полем `link`**, и
     `INSERT OR IGNORE` в `alerts` со `status='pending'`, сохраняя
     `route_id, price, depart_date, return_date, purchase_url,
     is_itinerary_specific, created_at, attempt_count=0,
     next_attempt_at=NULL` + `commit()` (идемпотентно на дубликате —
     устраняет REV-021: без этого шаг 6 не имел бы доступа к настоящей
     ссылке на тариф и всегда падал бы в общий фолбэк, даже когда точная
     ссылка была). Сама отправка сюда **не входит** — см. шаг 6.
  5. `record_price(conn, rid, entry)` — выполняется, если шаг 1 вернул
     непустой `entry`, независимо от результата шага 4.
  6. `flush_pending_alerts(conn, route, rid)` — **выполняется всегда, вне
     зависимости от результата шага 1** (устраняет REV-020) и вне
     зависимости от того, была ли аномалия именно в этом цикле (устраняет
     REV-017). Выбирает строки `alerts` с `route_id=rid AND status='pending'
     AND (next_attempt_at IS NULL OR next_attempt_at <= now)`. Для каждой:
     - если `now - created_at > ALERT_MAX_AGE_SECONDS` (по умолчанию 3600) —
       `UPDATE ... SET status='expired'`, лог уровня WARNING («тариф протух,
       пока алерт не удавалось доставить — вероятна долгая недоступность
       Telegram или неверный chat_id»), без попытки отправки (устраняет
       часть REV-022: не слать пользователю билет, которого уже нет);
     - иначе — собственный `try/except`: `send_telegram_alert(route,
       purchase_url, is_itinerary_specific, price, depart_date, return_date)`
       (текст и ссылка — из **сохранённых на шаге claim** полей, не из
       текущего `entry`) → при успехе `UPDATE ... SET status='sent'`; при
       исключении — `attempt_count += 1`, `next_attempt_at = now +
       min(EFFECTIVE_INTERVAL * 2 ** attempt_count, 3600)` (capped
       exponential backoff — устраняет вторую часть REV-022: без него
       заблокированный бот/неверный `chat_id` долбил бы Telegram API каждый
       цикл бесконечно), при HTTP 429 от Telegram — то же самое, но
       `next_attempt_at` берётся из заголовка `Retry-After`, если он есть.
       Статус остаётся `pending`, ни одно исключение наружу `check_route` не
       прокидывается (тот же принцип, что устранял REV-013).
  Детерминированный тест в `test_watcher.py` явно проверяет граничный
  случай: при ровно `MIN_HISTORY_SAMPLES - 1` предыдущих записях аномально
  низкая цена алерт не вызывает; при ровно `MIN_HISTORY_SAMPLES` — вызывает;
  а также случай «`send_telegram_alert` бросает исключение» — `record_price`
  всё равно должен быть вызван (мок считает вызовы). Отдельный тест
  проверяет REV-020 напрямую: `fetch_cheapest`-заглушка возвращает `None`,
  но заранее существующая `pending`-строка всё равно доставляется через
  `flush_pending_alerts` в этом же вызове `check_route`. Ещё один — что
  `claim_alert` сохраняет именно `purchase_url`/`is_itinerary_specific`,
  вычисленные из `entry["link"]`, и что `flush_pending_alerts` отправляет
  ровно их, а не пересчитывает заново (REV-021). Отдельный тест
  воспроизводит ровно сценарий REV-017: `send_telegram_alert` падает на
  первом вызове (алерт остаётся `pending`), затем несколько циклов подряд
  `check_route` вызывается с той же низкой ценой — после того, как эта цена
  несколько раз попадёт в `history` через `record_price`, скользящая медиана
  снижается настолько, что `is_anomaly` на шаге 4 перестаёт срабатывать; тест
  проверяет, что несмотря на это `flush_pending_alerts` (шаг 6) всё равно
  доставляет ранее отложенный алерт, как только заглушка `send_telegram_alert`
  перестаёт бросать исключение.

- **Персистентность всех наблюдений (устраняет REV-009)**: таблица `prices`
  получает колонку `actual INTEGER` (`1`/`0`/`NULL`, если поля в ответе не
  было). `record_price` пишет **любой** полученный `entry`, включая
  неактуальные — так критерий приёмки «каждое наблюдение пишется в БД»
  выполняется буквально. `get_recent_prices` (и только она) фильтрует
  `WHERE (actual IS NULL OR actual = 1)`, чтобы неактуальные записи не
  участвовали в медиане.

- **Дедупликация и порядок доставки — claim/flush разделены, с полным
  payload и backoff/expiry (устраняет REV-007, REV-017, REV-020, REV-021,
  REV-022)**: `alerts` содержит `route_id, price, depart_date, return_date,
  purchase_url, is_itinerary_specific, status ('pending'|'sent'|'expired'),
  created_at, attempt_count DEFAULT 0, next_attempt_at`,
  `UNIQUE(route_id, price, depart_date, return_date)`. Два независимых шага,
  специально **не связанные** друг с другом решением "аномальна ли цена
  именно в этом цикле" (это и было причиной REV-017), и **не вложенные**
  друг в друга по признаку "ответил ли API в этом цикле" (это было причиной
  REV-020):
  - **Claim** (шаг 4 `check_route`, только когда обнаружена новая аномалия):
    считает `purchase_url`/`is_itinerary_specific` из исходного `entry`
    **сейчас**, пока он ещё доступен (устраняет REV-021 — иначе flush не
    имел бы доступа к настоящей ссылке на тариф), и делает `INSERT OR
    IGNORE ... status='pending'` со всем payload'ом + `commit()`.
    Идемпотентно на дубликате, саму доставку не делает.
  - **Flush** (шаг 6 `check_route`, **каждый цикл, безусловно, даже если
    `fetch_cheapest` в этом цикле вернул `None`**, устраняет REV-020): для
    каждой готовой к попытке `pending`-строки этого `route_id` (см. фильтр
    по `next_attempt_at` и правило устаревания `ALERT_MAX_AGE_SECONDS`
    выше) — попытка `send_telegram_alert` из **сохранённых в самой строке**
    `price`/`depart_date`/`return_date`/`purchase_url`/`is_itinerary_specific`
    (не из текущего `entry` — на момент flush его может и не быть, если API
    только что ответил ошибкой); при успехе `status='sent'`; при
    исключении — `attempt_count`+1 и `next_attempt_at` со capped exponential
    backoff (или `Retry-After` при Telegram 429), статус остаётся `pending`
    — следующая попытка не раньше `next_attempt_at`, и **независимо от
    того, что покажет анализ аномалии в этом или будущих циклах** — ретрай
    недоставленных алертов, детекция новых аномалий и доступность
    Travelpayouts API теперь три разные, не блокирующие друг друга
    обязанности.
  Явно документированный компромисс (не полная ACID-транзакция с внешним
  HTTP-вызовом Telegram): при падении процесса ровно в окне между успешной
  отправкой и `UPDATE...SET status='sent'` возможен один дублирующий алерт —
  это редкий и безопасный край (не потеря данных, не финансовый риск),
  предпочтённый альтернативе «отметить перед отправкой и рисковать
  безвозвратно потерять алерт при обычном сбое сети к Telegram», что было бы
  значительно хуже для цели проекта. `# ponytail: at-least-once с редким
  дублем на краю "процесс упал между отправкой и UPDATE"; апгрейд — outbox с
  идемпотентным Telegram message key, если это когда-нибудь станет проблемой
  на практике.`
  **Явно закреплено в acceptance criterion 2 (устраняет REV-012)**: это не
  скрытое нарушение "не повторяет алерт", а осознанно принятое,
  задокументированное исключение из него — критерий приёмки прямо описывает
  оба случая (обычная работа/сбой сети → без дублей; аварийное падение
  процесса ровно в этом узком окне → допустим один дубль).

- **Сетевые таймауты (устраняет REV-014)**: `REQUEST_TIMEOUT_SECONDS=10` в
  `config.py`. **Каждый** вызов `requests.get`/`requests.post` — и к
  `api.travelpayouts.com`, и к `api.telegram.org` — передаёт
  `timeout=REQUEST_TIMEOUT_SECONDS`. Без этого `requests` по умолчанию не
  имеет тайм-аута и зависший TCP-коннект к любому из двух хостов заблокировал
  бы единственный процесс навсегда, включая все остальные маршруты и все
  будущие циклы. `requests.Timeout` — подкласс `requests.RequestException`,
  ловится той же веткой обработки, что и прочие сетевые ошибки; отдельного
  кода не требует.

- **Токены не должны попадать в логи (устраняет REV-018)**: `resp.
  raise_for_status()` формирует сообщение исключения, включающее полный URL
  запроса (`Response.url`) — для Travelpayouts это `?token=...`, для
  Telegram Bot API токен буквально часть пути (`/bot<TOKEN>/sendMessage`,
  так устроен сам Telegram Bot API, тут нет способа передать токен иначе).
  Наивный `log.exception(...)`/`log.error(f"...{e}")` на такое исключение
  запишет токен открытым текстом в systemd/journalctl — прямое нарушение
  требования «токены только в `.env`, никогда не в открытом виде где-либо
  ещё». Два взаимодополняющих исправления:
  - Токен Travelpayouts передаётся **заголовком** `X-Access-Token`
    (задокументированная и поддерживаемая альтернатива query-параметру
    `token` — см. `_dataapiv1.md`/`_dataapiv2.md`), а не query-параметром —
    тогда сам URL запроса к `api.travelpayouts.com` токен вообще не
    содержит, и класс утечки для этого хоста устранён на уровне
    транспорта, а не постфактум-редакцией.
  - Для Telegram (где токен неизбежно в URL по устройству самого Telegram
    Bot API) и как общая защита от невнимательности — вспомогательная
    функция `redact_url(url: str) -> str`, вырезающая значение параметра
    `token=` и сегмент пути `/bot<...>/ → /bot***/` регулярным выражением.
    Все места, где в лог может попасть URL или текст сетевого исключения
    (обработка `requests.HTTPError`/`RequestException` для обоих хостов),
    пропускают его через `redact_url`, и структурные логи по умолчанию несут
    только код статуса, хост, `route_id` — не сырой текст исключения
    (`log.error(...)` с явными полями, не `log.exception(e)` с полным
    traceback, который сериализует аргументы исключения как есть).
  Детерминированный тест в `test_watcher.py`: `redact_url` на URL с
  `?token=SECRET123` и на URL c `/bot123456:AAExampleTokenXYZ/sendMessage` —
  подстрока токена отсутствует в результате в обоих случаях.

- **Rate limiting — реально применяется, не только предупреждение
  (устраняет REV-008)**:
  - Эффективный интервал между полными циклами опроса вычисляется один раз
    при старте: `EFFECTIVE_INTERVAL = max(POLL_INTERVAL_SECONDS,
    ceil(len(ROUTES) * 60 / MAX_REQUESTS_PER_MINUTE))`. Если он больше
    настроенного `POLL_INTERVAL_SECONDS`, при старте — одна строка в лог с
    объяснением, и используется именно `EFFECTIVE_INTERVAL` для `time.sleep`
    между циклами. Бюджет запросов в минуту тем самым не превышается по
    построению, без токен-бакета/шедулера.
  - HTTP 429 не блокирует остальные маршруты того же цикла: при 429
    `fetch_cheapest` **не спит и не ретраит на месте** — сразу возвращает
    `None`, а `check_route` записывает в память (не в БД, простой
    `dict[route_id, float]` в процессе) время `next_allowed_at =
    monotonic() + retry_after` (из заголовка `Retry-After`, по умолчанию 60с
    если заголовка нет). На следующих циклах маршрут пропускается (без
    сетевого вызова, с логом) пока `monotonic() < next_allowed_at`. Так один
    заблокированный маршрут не задерживает опрос остальных в том же цикле.

- **Ссылка на билет — безопасная каноническая нормализация, и честно про
  даты в резервной ссылке (устраняет REV-010, REV-015 и REV-019)**:
  `startswith("http")` небезопасен как проверка доверия —
  `http://attacker.example/...` прошёл бы её и ушёл бы пользователю как
  "официальная" ссылка на билет при повреждённом/неверно распознанном ответе
  API. Вместо строковой проверки — разбор через `urllib.parse.urlparse` и
  allowlist хостов. Функция возвращает **пару** `(url, is_itinerary_specific)`
  — второй элемент явно говорит, ведёт ли ссылка на именно этот тариф/даты
  или на общий поиск по маршруту без предустановленных дат (REV-019: у
  `search.aviasales.ru` нет подтверждённых документацией параметров для
  дат конкретного тарифа — честнее прямо сказать об этом в сообщении, чем
  выдавать общий поиск за ссылку на алертнутый тариф):
  ```
  TRUSTED_LINK_HOSTS = {"aviasales.com", "www.aviasales.com",
                         "aviasales.ru", "www.aviasales.ru",
                         "search.aviasales.ru"}

  def build_purchase_link(route, entry):
      link = entry.get("link") if entry else None
      if link:
          parsed = urlparse(link)
          if parsed.scheme == "https" and parsed.netloc in TRUSTED_LINK_HOSTS:
              return link, True                 # доверенный абсолютный URL — конкретный тариф
          if not parsed.scheme and not parsed.netloc:
              path = link if link.startswith("/") else f"/search/{link}"
              return f"https://www.aviasales.com{path}", True  # относительный код/путь
          # неизвестная схема/хост — не доверяем, падаем в резервную ссылку
      url = (f"https://search.aviasales.ru/?marker={marker}"
             f"&origin_iata={route['origin']}&destination_iata={route['destination']}"
             f"&locale=ru")
      return url, False                         # общий поиск по маршруту, БЕЗ дат
  ```
  `send_telegram_alert`, если `is_itinerary_specific=False`, добавляет к
  сообщению короткую пометку («ссылка — общий поиск по маршруту без
  предустановленных дат, даты уточните на сайте»), а не молча выдаёт общую
  страницу поиска за ссылку на найденный тариф. Даты самого тарифа при этом
  и так уже есть в тексте сообщения (цена/даты формируются отдельно от
  ссылки, см. `send_telegram_alert`).
  Пять детерминированных тестов в `test_watcher.py`: относительный код без
  `/` (→ `True`), относительный путь с `/` (→ `True`), доверенный абсолютный
  URL (проходит как есть, → `True`), недоверенный абсолютный URL (например
  `http://attacker.example/...` или `https://evil.example/...` — обязан
  упасть в резервную ссылку, а не быть возвращён как есть, → `False`),
  отсутствие `link` вовсе (→ `False`).

### Файлы

- `config.py` — `ROUTES`: список словарей (`origin`, `destination`,
  `departure_at`, `return_at` (`None` для one-way), `one_way`, `currency`),
  собираемый одним списковым включением по матрице `ORIGINS × DESTINATIONS`
  (например, несколько аэропортов вылета в одном регионе — Нальчик,
  Минеральные Воды, Владикавказ, Грозный — против одного или нескольких
  направлений), а не переписыванием каждой комбинации вручную; `watcher.py`
  это не касается — он просто получает готовый список маршрутов любого
  размера. `ANOMALY_THRESHOLD=0.5`, `MIN_HISTORY_SAMPLES=5`,
  `HISTORY_WINDOW=30`, `POLL_INTERVAL_SECONDS=20`,
  `MAX_REQUESTS_PER_MINUTE=60`, `REQUEST_TIMEOUT_SECONDS=10`,
  `ALERT_MAX_AGE_SECONDS=3600`, `DB_PATH`. Токены — через `os.environ`, с
  собственным мини-загрузчиком `.env` (без зависимости `python-dotenv`, т.к.
  ТЗ требует минимум зависимостей).
- `watcher.py` — `route_id`, `init_db` (таблицы `prices` с колонкой `actual`
  и `alerts` со статусом `pending`/`sent`/`expired`, `purchase_url`,
  `is_itinerary_specific`, `attempt_count`, `next_attempt_at`), `redact_url`
  (см. REV-018), `fetch_cheapest` (запрос к `/aviasales/v3/prices_for_dates`,
  токен в заголовке `X-Access-Token`, `timeout=REQUEST_TIMEOUT_SECONDS`; на
  429 не блокирует, сразу возвращает `None` и сообщает `check_route` время
  следующей попытки по этому маршруту; различает «пусто» и «нераспознанная
  схема» в логах, см. REV-016; любой лог сетевой ошибки — только
  статус-код/хост/`route_id`, никогда сырой текст исключения или URL без
  `redact_url`), `get_recent_prices` (только `actual`-eligible),
  `record_price` (пишет всегда, если `entry` не `None`), `is_anomaly`,
  `build_purchase_link` (безопасная нормализация ссылки через allowlist,
  возвращает `(url, is_itinerary_specific)`, см. выше), `claim_alert`
  (считает и сохраняет полный payload алерта, включая ссылку, пока `entry`
  ещё доступен — REV-021) / `flush_pending_alerts` (доставка из сохранённого
  payload, с capped exponential backoff и `ALERT_MAX_AGE_SECONDS`-протуханием
  — REV-022; claim и доставка разделены — REV-017), `send_telegram_alert`
  (тоже с `timeout=REQUEST_TIMEOUT_SECONDS`, та же дисциплина логирования
  без сырых исключений), `check_route` (fetch → [если есть данные:
  decide-and-claim-on-prior-history → record] → flush-pending **безусловно,
  вне зависимости от того, были ли данные** — REV-020, см. выше), `main()` —
  бесконечный цикл со сном `EFFECTIVE_INTERVAL`; сетевые/API ошибки
  (`requests.RequestException`, включая `Timeout`) и любые прочие исключения
  на маршрут логируются
  (санитизированно) и не прерывают процесс.
- `test_watcher.py` — assert-based self-check без pytest/unittest: чистые
  функции (`is_anomaly` — включая граничные `MIN_HISTORY_SAMPLES-1` vs
  `MIN_HISTORY_SAMPLES`, `build_purchase_link` — 5 случаев ссылки, `route_id`,
  `redact_url` — 2 случая утечки токена), плюс детерминированные тесты
  `check_route` с `fetch_cheapest`, подменённым на функцию-заглушку (без
  реальной сети): аномальная цена →
  алерт ровно один раз; повторный вызов с той же ценой/датами → алерт не
  повторяется (дедуп), но `record_price` всё равно вызывается;
  `send_telegram_alert`-заглушка, кидающая исключение → `record_price` всё
  равно вызывается (REV-013).
- `.env.example`, `.gitignore` (`.env`, `prices.db`, `__pycache__`),
  `requirements.txt` (только `requests`), `README.md` (получение токенов,
  настройка `config.py`, запуск, первый реальный запуск для проверки полей
  ответа API, systemd unit, честные ограничения точности).

### Non-goals

- Скрейпинг сторонних сайтов.
- Множественные валюты/локали одновременно, мультипроцессность, очереди.
- Гарантия отлова всех "глюк-тарифов" — честно отражено в README.
- Продвинутый rate-limit шедулинг (общая очередь запросов, приоритизация
  маршрутов) — для 1–10 маршрутов достаточно предупреждения при старте.

## Assumptions and sources

- Существование `aviasales/v3/prices_for_dates` — подтверждено эмпирически
  (401 vs 404, см. выше), а не документацией.
- Параметры запроса — из независимого открытого исходного кода
  (`github.com/richarah/aviasales-python/blob/master/api.py`,
  функция `prices_for_dates`) и синтеза поисковой выдачи с примером полного
  URL запроса. **Не проверено напрямую по официальной HTML-документации** —
  `support.travelpayouts.com` был недоступен (DNS-ошибка) в рамках этой
  сессии.
- Имя параметра валюты (`currency` vs что-то иное) и точная схема полей
  ответа (особенно имя поля со ссылкой на билет) — **не подтверждены**,
  экстраполированы из остального семейства API. Явный риск, снижается
  защитным кодом (см. "Источник данных" выше) и обязательным первым живым
  запуском перед продакшен-использованием.
- Схема резервной ссылки поиска `search.aviasales.ru/?marker=&origin_iata=&destination_iata=`
  — из `_additional.md` (`github.com/travelpayouts/slate`), подтверждённый
  пример `choose_dates_url`.
- Telegram Bot API `sendMessage` (`POST https://api.telegram.org/bot<TOKEN>/sendMessage`,
  JSON body `chat_id`+`text`) — общеизвестный стабильный контракт, не
  проверялся отдельным запросом в рамках этой сессии.
- Риск: `prices_for_dates` — данные за последние 48 часов находок
  пользователей, а не live-цена в моменте; реальная задержка обнаружения
  зависит от того, как часто маршрут ищут другие пользователи Aviasales, а
  не от частоты нашего опроса. Это ограничение вынесено в README, а не
  решается кодом.
- Точный rate-limit для `aviasales/v3/prices_for_dates` не подтверждён
  документацией в рамках этой сессии — реализован консервативный
  конфигурируемый бюджет + корректная обработка 429, а не жёсткая цифра.

## Verification (proof commands)

```
python test_watcher.py
```
Ожидаемо: печатает `OK` без traceback, exit code 0. Включает детерминированные
тесты `check_route` на замоканном ответе API (успех/дедуп/сбой отправки/
граница `MIN_HISTORY_SAMPLES`) и 4 случая `build_purchase_link` — не требует
сети/токенов и надёжно проверяет anomaly+dedup+persistence+link-safety логику
без зависимости от реального рынка билетов.

Ручная проверка (не автоматизируется — нужны реальные токены):
1. **Первый запуск обязателен перед продакшен-использованием**: заполнить
   `.env` реальными токенами, запустить `python watcher.py` на один-два
   цикла, проверить в логе, что `fetch_cheapest` вернул распознанную цену
   (а не ERROR-строку о нераспознанной схеме, см. REV-016) — при
   необходимости поправить имена полей в `fetch_cheapest`/
   `build_purchase_link` по реальному ответу до продакшен-использования.
2. Временно поставить `ANOMALY_THRESHOLD=0.95` в `config.py`, дождаться
   `MIN_HISTORY_SAMPLES` циклов — наблюдательно, должно прийти сообщение в
   Telegram (не гарантируется ровно один цикл).
3. Отключить сеть на один цикл опроса — процесс не должен упасть, в логе
   должна появиться запись об ошибке в течение `REQUEST_TIMEOUT_SECONDS`,
   а не зависнуть бессрочно.
4. Перезапустить процесс — `prices.db` должен содержать прошлые наблюдения
   (`sqlite3 prices.db "select count(*) from prices"`), таблица `alerts`
   должна не дать повторно отправить уже отправленный (`status='sent'`)
   алерт.
